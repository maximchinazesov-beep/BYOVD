# GoFly64.sys — Анализ уязвимости типа BYOVD в драйвере с подписью Microsoft WHQL [не завершено]

Глубокий технический анализ драйвера сетевого фильтра режима ядра `GoFly64.sys`. Этот драйвер был разработан китайской компанией-разработчиком ПО (Nanjing Siyanrui Network Technology) и содержит крайне опасные примитивы, являющиеся **небезопасными по своей архитектуре (Insecure by Design)**; они позволяют осуществлять локальное повышение привилегий (LPE) и произвольное завершение процессов.

## 🔴 Парадокс безопасности: Подпись Microsoft WHQL
В отличие от типичных сторонних драйверов, подписанных стандартными коммерческими сертификатами, `GoFly64.sys` имеет официальную цифровую подпись от **Microsoft Windows Hardware Compatibility Publisher** (sha256).

![Подпись Microsoft WHQL](./assets/whql_signature.png)

### Сбой структурной валидации:
* **Абсолютное доверие:** Поскольку этот бинарный файл верифицирован компанией Microsoft, он «из коробки» полностью обходит механизм **принудительной проверки подписи драйверов (DSE)** в любой стандартной установке Windows 10 или 11.
* **«Слепота» антивирусов:** Традиционные решения класса EDR (Endpoint Detection and Response) и антивирусы (AV) воспринимают этот файл как доверенный компонент операционной системы, что приводит к крайне низкому уровню статического обнаружения (**~9/71 на VirusTotal**).

## 🛠️ Реконструированная карта IOCTL и примитивы эксплуатации

В ходе статического анализа с использованием инструмента IDA Pro мы составили карту основной процедуры диспетчеризации (`IRP_MJ_DEVICE_CONTROL`) и выявили несколько неаутентифицированных каналов управления, доступных напрямую приложениям пользовательского режима.

### 1. Примитив завершения процессов (`IOCTL 0x12227A`)
Эта процедура принимает идентификатор целевого процесса (PID) из буфера пользовательского режима без какой-либо проверки привилегий.
* **Внутренняя логика:** Драйвер явно использует системный вызов **`ZwOpenProcess`**, запрашивая права доступа `PROCESS_TERMINATE` (`1u`), после чего немедленно выполняет вызов **`ZwTerminateProcess`**.
* **Последствия:** Поскольку системные вызовы с префиксом `Zw` инициируются из режима ядра, операционная система игнорирует стандартные дескрипторы безопасности (ACL/DACL). Непривилегированные пользователи могут использовать этот IOCTL как оружие для мгновенного завершения работы защищенных решений безопасности (Windows Defender, Kaspersky, агенты EDR), тем самым «ослепляя» операционную систему.

### 2. Произвольная запись в память ядра / Примитив LPE (`IOCTL 0x122282`)
Критическая уязвимость типа «Write-What-Where» (запись произвольных данных в произвольное место), скрытая глубоко внутри обработчиков пользовательских команд.
* **Внутренняя логика:** Подпрограмма `sub_14000BC40` извлекает смещение в памяти и размер данных непосредственно из входного буфера, предоставленного пользовательским режимом. Она получает адрес назначения в памяти ядра с помощью внутренней вспомогательной функции и выполняет «слепую» операцию **`qmemcpy`** объемом до `0x104` байт.
* **Последствия:** Прямая произвольная перезапись памяти ядра без какой-либо проверки границ. Этот примитив предоставляет надежный вектор для атак типа **Token Stealing** (подмены токена доступа целевого процесса на токен процесса `System` с PID 4) с целью мгновенного локального повышения привилегий (LPE) до уровня `NT AUTHORITY\SYSTEM`.

### 3. Завершение работы драйвера и глобальное состояние гонки (TOCTOU)

Анализ процедуры деинициализации драйвера (`sub_14001322C`, привязанной к выгрузке драйвера или функции его завершения) выявляет критический архитектурный недостаток: **полное отсутствие синхронизации потоков (блокировок/спин-блокировок)** при работе с глобальной структурой `g_DriverContext`.

#### Логика процедуры завершения работы

```cpp
// Восстановленная процедура выгрузки
if ( g_DriverContext ) {
g_DriverContext->IsBusy = 0; // *((_DWORD *)g_DriverContext + 3) = 0; 
g_DriverContext->ActiveStatus = 0; // *((_DWORD *)g_DriverContext + 11) = 0;
}
UnregisterCallbacksOrNotify(&dword_140019510);
CleanupSystemResources();
CloseInternalHandles();

if ( g_DriverContext ) {
ExFreePoolWithTag(g_DriverContext, 0); 
g_DriverContext = NULL;
``` }
```

#### Уязвимость: Использование памяти после освобождения (Use-After-Free / UAF) в ядре / Ошибка проверки (BSOD)

Разработчик предпринимает попытку безопасно обнулить указатель `g_DriverContext` после освобождения пула памяти. Однако **указатель обнуляется слишком поздно**, что создает опасное «окно» между проверкой условия и его использованием (TOCTOU — Time-of-Check to Time-of-Use).

1. **«Окно» уязвимости**: В интервале между сбросом начального флага и фактическим вызовом `ExFreePoolWithTag` драйвер выполняет ряд ресурсоемких внутренних функций (от `sub_140014804` до `sub_140012A80`). На протяжении всего этого времени `g_DriverContext` остается полностью валидным указателем в памяти.
2. **Состояние гонки (Race Condition)**: Если приложение из пользовательского режима начинает интенсивно и параллельно отправлять запросы `IOCTL 0x12227E` (`UpdateDriverContext`) в тот момент, когда происходит выгрузка драйвера:
* Функция `UpdateDriverContext` выполняет проверку `if (g_DriverContext)`. Поскольку указатель еще не равен NULL, проверка **проходит успешно**. 
* В то время как `UpdateDriverContext` записывает данные, полученные из пользовательского режима, в поля структуры, поток выгрузки драйвера инициирует вызов `ExFreePoolWithTag`. 
* **Результат**: Функция `UpdateDriverContext` выполняет операции записи в память пула ядра, которая уже была освобождена; это приводит либо к немедленной **ошибке проверки (Bug Check / BSOD)**, либо к локальному повреждению пула памяти.

### 4. Обработчик раскрытия произвольной памяти ядра (`sub_14000BC40`)

Драйвер предоставляет недокументированный примитив, позволяющий клиентам из пользовательского режима считывать произвольные блоки памяти непосредственно из адресного пространства ядра. Это приводит к возникновению серьезной уязвимости, связанной с раскрытием информации, и позволяет злоумышленникам обойти KASLR или допустить утечку учетных данных/токенов.

#### Расширенная карта маршрутизации IOCTL

Ниже представлена ​​полная карта экосистемы IOCTL, обнаруженная в процедуре диспетчеризации:


| Код IOCTL (HEX) | Метод передачи | Минимальный размер входных данных | Основная функциональность |
| :--- | :--- | :--- | :--- |
| `0x12226E` | `METHOD_BUFFERED` | Неизвестно | Первичная валидация / Проверка устройства |
| `0x122272` | `METHOD_BUFFERED` | 6 байт | Обновление конфигурации/буфера через `qmemcpy` |
| `0x122276` | `METHOD_BUFFERED` | 8 байт | Регистрация / Инициализация объектов |
| `0x12227A` | `METHOD_BUFFERED` | 4 байта | **КРИТИЧНО**: Произвольное завершение процессов (`ZwTerminateProcess`) |
| `0x12227E` | `METHOD_BUFFERED` | 4 байта | Обновление глобального контекста (`UpdateDriverContext`) |
| `0x122282` | `METHOD_BUFFERED` | `0x104` байта | **КРИТИЧНО**: Утечка памяти ядра / Обработчик произвольного чтения |
| `0x122286` | `METHOD_BUFFERED` | Неизвестно | Очистка после операций / Метрики |

#### Анализ уязвимости: Произвольное чтение (`0x122282`)

При анализе обработчика, назначенного блоку операций с памятью (`sub_14000BC40`), путь выполнения корректно извлекает базовые адреса отображений объектов ядра, однако не выполняет валидацию ограничений для адреса назначения:

```cpp
// Восстановленный уязвимый код
v3 = findKernelObjByIndex(6581875164, inputBuffer + 1, *inputBuffer);
sub_14000D578(&unk_140019478, v6, &v4);
v1 = sub_14000D200(&unk_140019478, v7);

``` if ( !sub_14000B16C(v6, v1) ) {
// Вектор эксплуатации: 260 байт утекают непосредственно в буфер ввода пользовательского режима
qmemcpy(inputBuffer, getTargetKernelAddress(&unk_140019478, &v5), 0x104);
}
return GetFinalStatus(v8);
```

#### Краткое описание эксплуатации
Злоумышленник может сформировать полезную нагрузку, указав в первых байтах буфера ввода определенный индекс или токен. Драйвер внутренне разрешает целевой адрес и выполняет операцию прямого копирования памяти (`qmemcpy`), передавая ровно `260 байт` (`0x104`) из структуры состояния ядра обратно в буферизированный канал взаимодействия с пользовательским пространством, без какой-либо проверки границ.

#### Приложение: Примитив доступа к файловой системе (`sub_1400073BC`)

Чтобы избежать срабатывания фильтров файловой системы пользовательского режима и стандартных механизмов контроля доступа, драйвер использует собственную обертку уровня ядра для нативного API `ZwCreateFile`.

```cpp
// Восстановленная обертка ядра для создания/открытия файлов
int64_t __fastcall KernelCreateFile(
struct _IO_STATUS_BLOCK *IoStatusBlock,
struct _UNICODE_STRING *ObjectPath,
void *SecurityDescriptor,
ACCESS_MASK DesiredAccess,
int Attributes,
ULONG FileAttributes,
ULONG ShareAccess,
ULONG CreateDisposition,
ULONG CreateOptions,
PLARGE_INTEGER AllocationSize)
{
struct _OBJECT_ATTRIBUTES ObjectAttributes; 

ObjectAttributes.Length = 48; // sizeof(OBJECT_ATTRIBUTES) на x64
ObjectAttributes.RootDirectory = NULL; 
ObjectAttributes.Attributes = Attributes; 
ObjectAttributes.ObjectName = ObjectPath; 
ObjectAttributes.SecurityDescriptor = SecurityDescriptor; 
ObjectAttributes.SecurityQualityOfService = NULL; 

// Прямой вызов в обход границ безопасности пользовательского режима ОС
return ZwCreateFile(
(PHANDLE)&IoStatusBlock[1],
DesiredAccess,
&ObjectAttributes,
IoStatusBlock,
AllocationSize,
FileAttributes,
ShareAccess,
CreateDisposition,
CreateOptions,
NULL,
0);
}
```

Это гарантирует, что любой запрос к файловой системе, нацеленный на `\SystemRoot\System32\drivers\etc\hosts`, будет выполнен напрямую через исполнительную подсистему ядра, оставляя минимальное количество следов для высокоуровневых инструментов мониторинга поведения в пользовательском режиме.
